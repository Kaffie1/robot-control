# 故障排查文档

这份文档用于机器人故障排查对话，也用于后端构造 LLM 上下文。

## 目标

1. 让外部人员只描述现象即可
2. 让模型优先做只读诊断
3. 让模型输出可执行命令
4. 让后端执行命令后把结果回灌给模型继续判断

## 提问方式

外部人员不需要填写完整报告，直接说现象就行，例如：

- 导航时底盘不动
- 没有定位
- topic 没数据
- service 调用失败
- 升级后异常
- 地图加载失败

如果模型判断信息不够，会再追问一两个最关键的问题。

## 案例

### 没有定位

建议按下面的顺序排查：

1. 先检查激光相关 topic 有没有数据，确认传感器链路和 ROS 发布是否正常
2. 再检查系统里有没有设置 `D_floor` 地图，确认定位使用的地图配置是否正确
3. 如果激光有数据，且 `D_floor` 也已经正确设置，但还是没有定位信息，就停止自动排查，直接找算法同事继续分析

这个案例对应的 playbook 位于 `config/fault_playbooks.yaml` 里的 `no-localization`。

对应的执行思路可以理解成先查 `/livox/lidar`，再查 `/zj_humanoid/navigation/odom_info`，最后确认 `D_floor` 配置。

当激光和地图都正常，但仍然没有定位时，模型应输出 `final`，并用更适合现场阅读的布局收敛结论，而不是把工具返回结果原封不动贴出来。

注意：所有 ROS 命令都应该走 rosbridge 容器里的 ROS 工具，不要让模型输出 `docker exec ... rostopic ...` 这种命令。`execute_remote_command` 只用于非 ROS 的主机级只读检查。

## 排查原则

1. 先只读，后恢复
2. 优先选择最便宜、最可验证的步骤
3. 没有连接上下文时，不允许生成恢复动作
4. 信息不足时先澄清，不要直接猜原因
5. 如果可能是硬件问题，要明确提示人工检查

## 输出流程

模型在对话中应遵循下面的闭环：

1. 读取故障描述和上下文
2. 判断是否需要补充信息
3. 如果需要采集信息，输出结构化命令
4. 后端执行命令
5. 后端把结果回灌给模型
6. 模型继续分析，直到给出最终结论

## 可执行工具

可执行工具由后端工具注册表提供，实际执行时会走当前已连接机器人的 SSH 远端命令。
当前聊天页会自动把工具列表放入上下文。

如果要扩展工具能力，优先在 `backend/agent_tools.py` 里增加实际实现，再同步更新故障工具文档。
